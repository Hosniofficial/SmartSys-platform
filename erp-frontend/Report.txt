Redesign → Original Functional Parity Checklist

Scope: This report documents every functional difference found between the original and redesigned versions across all 20 matched page pairs. Only files with actual functional differences are listed. Pure visual/styling changes are excluded per instructions and are only counted in the summary.

1. FILE: Cashier Dashboard (CashierDashboard.vue)
Issue 1.1 — Manual Shift Open/Close Removed
Location: <script setup> — functions openShift, closeShift; template — shift control buttons in header
What exists in original: Full manual shift lifecycle: isOpeningShift, isClosingShift, shiftOpeningAmount, shiftClosingAmount, shiftNotes refs; openShift() and closeShift() functions calling shiftStore.openShift()/shiftStore.closeShift(); small +/× buttons next to "وردية تلقائية" label allowing manual override of the automatic shift.
What is missing in redesign: All of the above — functions, refs, and buttons are completely removed. Comment in redesigned file states shift is now "100% automatic."
Why required: If any workflow depends on manually opening/closing a shift independent of the session (e.g., correcting a shift that didn't auto-create, or splitting a shift mid-session), that capability is gone.
How to restore: Re-add isOpeningShift, isClosingShift, shiftOpeningAmount, shiftClosingAmount, shiftNotes refs; re-add openShift()/closeShift() functions calling shiftStore.openShift()/shiftStore.closeShift(); re-add the manual override buttons in the header shift-pill.
Priority: High (confirm with product owner first — may be an intentional deprecation, but must be confirmed before deleting the restore work)
Issue 1.2 — Device Rename Feature Removed
Location: <script setup> — functions openRenameDevice, saveDeviceName; template — "تسمية الجهاز" button and Rename Device modal
What exists in original: Button in header opens a modal (showRenameDevice) with input bound to deviceNameInput; saveDeviceName() persists to localStorage['pos_device_name'].
What is missing in redesign: Button, modal, and both functions are entirely absent.
Why required: Users lose the ability to label POS terminals/devices for identification in session/shift records.
How to restore: Re-add showRenameDevice, deviceNameInput refs; re-add openRenameDevice()/saveDeviceName() functions; re-add button + modal to template.
Priority: Medium
Issue 1.3 — Recent Activities Data Source Changed
Location: fetchDashboardData() — activity mapping block
What exists in original: Maps data.latest[] (sales-only records) into recentActivities, with single icon/color (fa-receipt, emerald).
What is missing in redesign: Now maps data.recentActivities[] — a different field name — with type-aware icon/color branching for sale/return/withdrawal/deposit.
Why required: If the backend response was not updated to emit a recentActivities field (only latest), the "Recent Activities" panel will silently render empty in the redesigned page.
How to restore: Verify with backend team that the API response includes recentActivities with a type field before shipping. If not present, either (a) update backend to emit this field, or (b) revert the frontend mapping to use data.latest.
Priority: Critical (silent data-loss risk if unverified)
Issue 1.4 — Admin Branch Selection Moved Out of Session Modal
Location: Open Session modal — admin branch selector
What exists in original: Admin picks the branch inside the "Open Session" modal via an editable <select v-model="modalSelectedBranchId">.
What is missing in redesign: Modal now shows the branch read-only, sourced from the header's adminSelectedBranch. Admin must select branch from the header dropdown before opening the session modal.
Why required: This is a workflow change — if an admin opens the modal without first setting the header branch, they can no longer choose it in-context.
How to restore: Either (a) accept this as an intended UX change (confirm with product), or (b) re-add the in-modal editable branch <select> bound to a modal-local variable as in the original.
Priority: High (must be a confirmed product decision, not a silent change)
Issue 1.5 — New Terminal-Existence Validation Added
Location: triggerOpenSession()
What exists in original: No check for terminal existence before opening the session modal.
What is missing/added in redesign: New logic fetches terminals and blocks session opening with a toast if none exist for the branch; also auto-selects the first terminal.
Why required: This is new, stricter behavior not present in the original. For strict functional parity, this guard should be flagged as an addition — not a bug — but it changes what previously succeeded into a blocked action.
How to restore: If strict parity to original is required, remove the terminal-existence blocking check. Recommended: keep as a genuine improvement, but confirm with product before finalizing since it changes existing behavior for branches without terminals configured.
Priority: Medium (behavior change requiring product sign-off, not a defect)

5. FILE: Cash Vouchers (CashVouchers.vue + VoucherForm.vue)
Issue 5.1 — Edit-Modal Branch ID Fallback Removed
Location: Original openEditModal(v); Redesigned onEditVoucher(v)
What exists in original: When opening the Edit modal, if the voucher record has no branch_id (legacy data), the code explicitly derives a fallback: branchIsolation.getRequiredBranchId() for non-exempt (cashier) users, or branchStore.selectedBranchId for exempt (admin) users — then validates the derived ID against the branches list before assigning it.
What is missing in redesign: onEditVoucher simply does form.value = { ...v, payment_to_type: ... } with no fallback logic for a missing branch_id.
Why required: Editing an old/legacy voucher record that lacks a branch_id will now fail the "branch is required" validation on submit, where the original page would have self-healed by deriving a valid branch.
How to restore: Add back the fallback logic in onEditVoucher/openEditModal: if !v.branch_id, derive it via branchIsolation.getRequiredBranchId() (non-exempt) or branchStore.selectedBranchId (exempt), validate against branches.value, and assign before opening the modal.
Priority: Critical (breaks editing of legacy records)
Issue 5.2 — Edit-Modal Auto-Link Account-from-Payment-Method Removed
Location: Original openEditModal(v) — post-assignment account linking block
What exists in original: After populating editForm, if editForm.value.payment_method_id is set but editForm.value.account_id is missing, the code looks up the matching payment method in validPaymentMethods and assigns its account_id.
What is missing in redesign: This auto-link-on-open logic is absent. The redesigned form only re-derives account_id reactively via updateAccount(), which fires on the payment method <select>'s @change event — not when the modal first opens.
Why required: Legacy vouchers with a payment method but no linked account will have account_id empty when the edit modal opens, and will stay empty unless the user manually re-selects (or re-confirms) the payment method dropdown. This can block submission (form requires a linked account) or submit with a missing account link.
How to restore: Add an onMounted/immediate-effect check in VoucherForm.vue (or in onEditVoucher before showing the modal) that re-derives account_id from payment_method_id if not already set, mirroring the original's post-assignment block.
Priority: Critical (breaks editing of legacy records, potential silent submission errors)
Issue 5.3 — Payload Sends Explicit null Instead of Omitting Fields
Location: Original submitAddVoucher/submitEditVoucher payload construction; Redesigned VoucherForm.vue → handleSave()
What exists in original: Uses conditional object spreads so that, e.g., for a payment-type voucher, the customer_id/sale_id keys are entirely absent from the JSON payload.
What is missing/changed in redesign: handleSave() explicitly sets these fields to null (e.g., payload.customer_id = null; payload.sale_id = null;) rather than omitting them.
Why required: If the backend distinguishes "field omitted" from "field explicitly null" (common in PATCH-style partial-update APIs or strict schema validators), this could cause different backend behavior (e.g., clearing a field that should have been left untouched).
How to restore: Verify with backend team whether the voucher create/update endpoints treat omitted vs. null fields differently. If they do, change handleSave() to delete payload.customer_id / delete payload.sale_id etc. instead of assigning null.
Priority: High (verify before ship — data integrity risk)
Issue 5.4 — Branches No Longer Refreshed on Every Modal Open
Location: Original fetchLists() called from onAddVoucher/openEditModal; Redesigned fetchLists() in onMounted only
What exists in original: fetchLists() (which includes branchStore.fetchBranches()) is called every time the Add or Edit voucher modal is opened.
What is missing in redesign: Branches are fetched once on page mount only; opening the modal does not re-fetch them.
Why required: If a branch is added/modified elsewhere in the system while the Cash Vouchers page is open, the original would pick up the change on next modal open; the redesign will show stale branch data until a full page reload.
How to restore: Add branchStore.fetchBranches() (or a full fetchLists() call) into onAddVoucher() and onEditVoucher() in the redesigned page.
Priority: Low
Issue 5.5 — New Client-Side Amount Validation Added
Location: VoucherForm.vue → validateForm()
What exists in original: No explicit script-level check that amount > 0; only enforced via HTML input attributes (bypassable).
What is missing/added in redesign: New check: if (!localForm.value.amount || Number(localForm.value.amount) <= 0) { localError.value = '...'; return false; }
Why required: This is a new safety validation not present in the original. For strict identical behavior it should be flagged, though it is a net improvement.
How to restore: No removal recommended. Confirm with product/QA that this stricter validation is acceptable (it will block previously-possible zero/negative amount submissions, if any existed).

// ─── Shift Actions (منطق غير مُغيَّر — فقط عُرضت بصرياً بشكل مختلف في الـ Header) ──
const openShift = async () => {
  if (isOpeningShift.value) return;
  try {
    let wid = null;
    try {
      wid = branchIsolation.getRequiredBranchId();
    } catch (e) {
      showToast(e.message || 'الرجاء اختيار الفرع قبل فتح الوردية', 'error');
      return;
    }
    if (!wid) { showToast('الرجاء اختيار الفرع قبل فتح الوردية', 'error'); return; }
    if (!selectedTerminalId.value) { showToast('الرجاء اختيار جهاز نقطة البيع', 'error'); return; }
    isOpeningShift.value = true;
    const result = await shiftStore.openShift({
      branch_id: String(wid),
      terminal_id: selectedTerminalId.value,
      opening_cash_amount: Number(shiftOpeningAmount.value) || 0,
      notes: shiftNotes.value || undefined
    });
    if (result?.status === 'success') {
      currentShift.value = result.data || null;
      shiftOpeningAmount.value = 0;
      shiftNotes.value = '';
      showToast('تم فتح الوردية بنجاح', 'success');
    } else {
      showToast(result?.message || 'تعذر فتح الوردية', 'error');
    }
  } catch (e) { showToast(e?.response?.data?.message || 'تعذر فتح الوردية', 'error'); }
  finally { isOpeningShift.value = false; }
};

const closeShift = async () => {
  if (isClosingShift.value || !currentShift.value?.id) { showToast('لا يوجد وردية مفتوحة', 'info'); return; }
  try {
    isClosingShift.value = true;
    const result = await shiftStore.closeShift({
      shift_id: currentShift.value.id,
      closing_cash_amount: Number(shiftClosingAmount.value) || 0,
      notes: shiftNotes.value || undefined
    });
    if (result?.status === 'success') {
      currentShift.value = null;
      shiftClosingAmount.value = 0;
      shiftNotes.value = '';
      showToast('تم إغلاق الوردية بنجاح', 'success');
    } else {
      showToast(result?.message || 'تعذر إغلاق الوردية', 'error');
    }
  } catch (e) { showToast(e?.response?.data?.message || 'تعذر إغلاق الوردية', 'error'); }
  finally { isClosingShift.value = false; }
};
